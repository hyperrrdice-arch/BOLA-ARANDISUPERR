# QA, penerimaan, dan rilis

**Untuk setiap PR.** Jalankan skenario yang relevan di checkout bersih, Node 24, zona waktu proses UTC, dan data sementara yang dapat dibuang. Jalankan uji waktu/antarmuka lagi dengan zona Asia/Jakarta. Catat SHA, versi aktual Node, lockfile, seed, kumpulan data dan waktu mulai/selesai. Ketika tes gagal, perbaiki produser atau pembaca di jalur yang dipakai aplikasi.

## K0 · Membuat hasil uji bisa dipercaya

1. Buka `.github/workflows/ci.yml`, `package.json`, skrip yang dipanggil, dan penggunaan `node:sqlite`. Pada commit audit, CI memilih Node 20, memanggil tiga skrip yang sudah tidak ada dan belum membangun aplikasi. Petakan setiap maksud tes lama ke assertion aktif. Tulis uji pengganti untuk kontrak mapper, vig dan nilai yang masih dipakai. Jangan membuat tiga file kosong agar workflow hijau.
2. Tetapkan Node 24 dalam CI serta lingkungan eksperimen. Jalankan `npm ci`, `npx --no-install tsc --noEmit`, lalu suite baru. Untuk memanggil suite yang **sudah ada**, gunakan `npx --no-install tsx scripts/quant-correctness-tests.ts` dan `npx --no-install tsx scripts/pick-engine-acceptance.ts` melalui runner fixture. Yang kedua menulis artefak ke `tasks`; arahkan output ke sandbox uji. Pemeriksaan selisih atau kebocoran yang hanya mencetak peringatan harus menghasilkan exit code gagal saat melampaui batas.
3. Siapkan helper pengujian yang membuat direktori data unik per run, membangun skema dengan kode sebenarnya dan memasukkan data minimal. Untuk suite saat ini, sediakan liga, dua tim dan beberapa pertandingan final sebelum/sesudah cutoff. Gunakan dua laga dan hasil terpisah untuk D01. Jangan membiarkan suite lolos dengan nol baris; cek jumlah yang **harus** diuji. Provider fixture, jam, lokasi database dan lokasi output dapat diinjeksi tanpa koneksi ke VPS.
4. Buat perintah npm stabil **sebagai pekerjaan K0**: `npm run test:quant`, `npm run test:data`, `npm run test:web` dan `npm run test:e2e`. Hubungkan ke implementasi tes yang benar. Pakai `npm run lint`, typecheck, suite dan `npm run build` di CI. Pastikan build dapat memakai aset font yang diizinkan runner; bila pengambilan font menghalangi build offline, sediakan aset lokal berlisensi atau fallback.
5. Jalankan dua kali dari data baru. Pastikan assertion yang sengaja dirusak benar-benar memerahkan job. Simpan baseline D01 yang gagal di kode lama bersama log ringkas dan reproduksinya. K1 mengubahnya menjadi regresi wajib yang hijau; hindari `skip` permanen untuk menutupi masalah. [Workflow](https://github.com/hyperrrdice-arch/BOLA-ARANDISUPERR/blob/b9b38713b214f4e34c5e56c4cb5c222e4ab50c64/.github/workflows/ci.yml) · [suite quant](https://github.com/hyperrrdice-arch/BOLA-ARANDISUPERR/blob/b9b38713b214f4e34c5e56c4cb5c222e4ab50c64/scripts/quant-correctness-tests.ts) · [suite pilihan](https://github.com/hyperrrdice-arch/BOLA-ARANDISUPERR/blob/b9b38713b214f4e34c5e56c4cb5c222e4ab50c64/scripts/pick-engine-acceptance.ts).

| D09 | Publikasikan tiket resmi dua laga, susun slip browser dengan isi yang sama, ulang edisi yang sama; jalankan resolver pada kombinasi hit/hit, hit/miss, hit/void, miss/void, miss/pending. | Satu tiket resmi per slot/edisi. Status berturut-turut hit, miss, void, miss, pending sampai terminal. Pilihan user dikecualikan dari statistik resmi. Alias ganda tidak menambah leg. Uji kontrak API tambahan memakai data sementara. Simpan snapshot respons minimal dari empat endpoint di bab Data, cek status dan bentuk response saat sukses, kosong, parameter invalid, provider gagal dan row legacy. Untuk agen, cek normal/debug dan bahwa GET tidak menambah official ledger. Untuk odds, cek pasangan quote normal dan `bookmakers=null`. Bedakan tidak tersedia dari harga nol.

## Q01–Q04 · Kebenaran hitung, model dan eksperimen

| ID | Input | Assertion wajib |
|---|---|---|
| Q01 | Matriks 3×3 pada data contoh, sumbu baris gol kandang, kolom gol tamu. Turunkan rumah/seri/tamu, double chance dan dua kejadian yang saling meniadakan. | Jumlah sel = 1; 1X2 = 0,47 / 0,40 / 0,13; 1X = 0,87. Irisan kandang menang dengan 1X = 0,47; kandang menang dengan tandang menang = 0. Gunakan toleransi `1e-8` untuk contoh ternormalisasi. |
| Q02 | Gunakan dua paket beku dan input sama melalui jalur produksi, evaluasi dan pembaca pasar. Masukkan nol, NaN, peluang negatif, odds ≤1 dan nilai hilang. | Versi dan fallback sama. Selisih probabilitas normal ≤ `1e-8`; tolak atau tandai invalid sesuai kontrak field. Nilai nol probabilitas tetap nol. Audit dua paket menemukan 20/20 probabilitas konsisten; jalankan ulang pada checkout saat ini. |
| Q03 | Sisipkan observasi masa depan dengan `available_at` melebihi keputusan, termasuk gol ekstrem, harga, registry atau fit dari masa depan. Uji input bertanggal tanggal-saja dan dua kickoff bersamaan. | Snapshot dan prediksi historis lama identik. Observasi yang sah sebelumnya dapat mengubah fitur yang tepat. Semua laga fisik dan alias satu pertandingan tetap pada blok waktu yang sama. |
| Q04 | Dua alias mewakili pilihan 80% yang sama. Dua pertandingan berbeda 80% dan 70%. Dua predikat laga yang sama dengan matriks tersedia/tidak tersedia. Jalankan evaluasi dua kali dengan manifest sama. | Alias → satu pilihan 80%; laga berbeda → 56% beserta asumsi; satu laga → irisan matriks atau alasan kosong. Dua evaluasi regenerasi menghasilkan baris prediksi dan keputusan promosi sama, toleransi numerik terdokumentasi. |

K5 mengirim manifest as-of, checksum input, baris prediksi kedua model, log-loss/Brier/kalibrasi/cakupan, interval bootstrap dan putusan `promote`, `retain` atau `inconclusive`. Laporkan penyebut liga, piala, pasar dan harga yang cocok. Menggabungkan kandidat memerlukan hasil di holdout yang memenuhi aturan bab Model dan review atas dampak operasional.

## Anggaran performa dan pemantauan

| Jalur | Baseline audit dan syarat rilis yang diusulkan |
|---|---|
| Jadwal, 10 vs 75 fixture | Pengukuran lokal lama menemukan 76 statement untuk 75 fixture. Target ≤8 eksekusi SQL untuk masing-masing ukuran setelah pembukaan store dan migrasi selesai. Instrumentasi `prepare` serta `all/get/run` agar prepare sekali di loop tidak menyamarkan N+1. Hitung seluruh store yang disentuh oleh request. |
| Bukti dan landing | Kueri bukti lama sekitar 302–374 ms pada fixture ~163 ribu baris. Ukur 10 run pemanasan lalu 100 request per filter di mesin/versi dan dataset tetap. Sasaran awal untuk pembacaan statistik hangat: median ≤100 ms dan p95 ≤150 ms. Laporkan dingin terpisah; lampirkan `EXPLAIN QUERY PLAN`, indeks dan biaya tulis. |
| Invalidasi | Publish satu pilihan, koreksi hasil tanpa mengubah jumlah row, ganti filter/periode, dan panggil dari proses kedua. Uji nilai baru segera setelah generasi terbit. Kunci cache memakai versi/koreksi dan filter; pencacahan row atau TTL saja dapat memberi hasil salah. |
| Web | Di lapangan, target p75 per perangkat untuk LCP ≤2,5 s, INP ≤200 ms, CLS ≤0,1. Sebelum ada sampel lapangan, gunakan trace loading berulang dengan profil ponsel yang didokumentasikan dan interaksi Playwright untuk regresi; laporkan sebagai data lab. Periksa perbedaan ukuran JS dan hilangnya aset hero 3D dari jalur awal. [Definisi Web Vitals](https://web.dev/articles/vitals). |

Catat per tahap dan per provider jumlah parsed, invalid, cocok/ambigu, final, pending jatuh tempo beserta umur/alasan, pasar pra-laga yang memenuhi syarat, paket, pilihan resmi, tiket resmi, dan cap publikasi terakhir yang bisa dibaca UI. Pisahkan zero eligible dari kegagalan provider atau input kedaluwarsa. Log terstruktur memuat run ID, fixture UID bila ada, versi dan durasi. Simpan ringkasan tanpa credential, raw auth header atau input sensitif.

## Migrasi, peluncuran dan kembali ke versi sebelumnya

1. **Inventaris.** Catat skema, jumlah, unique key, keterhubungan row, versi migrasi, status WAL dan volume. Buat backup konsisten memakai SQLite backup API atau snapshot terkoordinasi yang didukung deployment; salinan `.db` sendirian saat writer aktif dapat melewatkan WAL. Uji restore di lingkungan terpisah dengan `integrity_check` dan perbandingan jumlah. [SQLite Backup API](https://www.sqlite.org/backup.html).
2. **Perluas skema.** Tambahkan tabel/kolom nullable dan indeks idempoten. Backfill per batch dengan checkpoint, checksum dan alasan hasil tiap row. Pertahankan ID lama dan histori revisi. Jika proses berhenti di tengah, ulang dari checkpoint dan bandingkan jumlah akhir. Simulasikan dua writer. Hindari mengarang waktu terbit atau probabilitas historis.
3. **Baca ganda di staging.** Bandingkan lama dan baru pada hasil akhir, total pilihan unik, probabilitas yang bisa dibuktikan, row ambigu, waktu muat, dan hasil per route. Setiap selisih harus dapat dijelaskan oleh fixture. Jalankan satu putaran penuh menggunakan provider lokal beku dari impor → data → paket → ledger → resolver → halaman. Jalankan putaran kedua sebagai uji idempotensi.
4. **Rilis bertahap.** Urutan yang diusulkan adalah pembaca kompatibel, penulis data berversi, penyajian rekam hasil, lalu frontend. Konfigurasi memilih versi pembaca/penulis aktif. Pantau dua siklus publikasi lengkap di staging yang mencakup setidaknya satu hasil final dan satu kasus data parsial. Kelulusan UI memerlukan D/U yang relevan; kelulusan challenger memiliki keputusan sendiri. Hasil minim di kompetisi kecil diberi label ukuran sampel.
5. **Jika ada regresi.** Hentikan promosi writer/model baru di konfigurasi rilis yang berwenang; kembalikan pembaca ke versi kompatibel. Pertahankan row baru dan histori terbit. Rekonsiliasi operasi yang tertunda, bandingkan total dan rerun smoke. Restore backup hanya dalam prosedur pemulihan yang telah diuji dan setelah mempertimbangkan penulisan sah sejak backup. Penyimpangan runtime VPS ditangani oleh pemilik di luar PRD ini.
6. **Bukti yang diserahkan.** Isi ringkasan PR dengan masalah, fixture pembuktian, file berubah, perintah dan hasil nyata, ukuran data, selisih sebelum/sesudah, pemulihan serta pekerjaan tertunda. Jika satu gate gagal, tulis ID gate dan dampaknya, lalu pertahankan versi yang telah diterima.

### Checklist penerimaan pemilik

- Dari jadwal buka satu laga dengan analisis, satu tanpa harga dan satu tanpa paket. Buka satu URL alias lama. Nama tim, skor/jam dan arti peluang konsisten.
- Dari rekam hasil pilih satu tiket dan satu pilihan yang sudah selesai. Telusuri hingga jam terbit, snapshot dan skor 90 menit. Ulangi setelah satu koreksi resmi di staging.
- Baca keputusan eksperimen tanpa membuka kode. Harus terlihat jumlah laga, batas waktu latih, baseline yang dibandingkan, perubahan skor, interval dan alasan memilih versi.
- Periksa jejak catatan sinkronisasi repo untuk perbaikan refresh. Catatan bisa berstatus menunggu diff tersanitasi; penerimaan fitur lain bergantung pada pengujian aplikasinya sendiri.
